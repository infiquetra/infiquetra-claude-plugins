# Jev / TypeSafe AI coding-agent integrations: a survey for the Claude Code / Codex / Gemini / Qwen plugin fleet

## Orientation: read every number below against a three-day-old ecosystem

Jev is the first "System One" model from TypeSafe AI (`typesafe.ai`): instead of generating text, it returns typed probability judgments — a yes/no probability called Noul, a labeled pick from a fixed set called Choice, and a position on an ordered rubric called Score. Per `github.com/kraayenjon/awesome-jev` (fetched from repo), Jev launched in early access on September 15, 2026 — three days before this research was done. Every project below is, at most, a long weekend old; star counts and "measured" tables are early, self-reported signals, not settled consensus. A number corroborated by two or more independent projects (the $0.042-per-million-input-token price; roughly 130-500 millisecond latency) is noted as such; a single-source number is flagged too.

Everything below is **fetched-from-repo** (read directly from a README, plugin manifest, or hook configuration file on GitHub) unless marked **snippet-only** (a WebFetch summary of a page, not a raw file I read myself). The two madewithjev.com "build" write-ups are snippet-only throughout.

## 2. Mechanism, project by project

**jev-router** wraps rather than hooks: `jev-claude` and `jev-codex` start a loopback proxy, launch the real command-line interface (CLI) unmodified, and forward its existing login. One Jev call per fresh turn picks an abstract tier (fast/balanced/strong/long), mapped to a concrete model per CLI. It writes up to 20 recent routing exchanges — including "prompt text and Jev's exact request and response" — to plaintext JavaScript Object Notation (JSON) files in the operating system's temp directory.

**fast-jev-compaction** replaces Claude Code's `/compact` summary with the original messages minus stale tool output: "This library never rewrites anything. It only deletes tool calls and tool results Jev says are no longer needed." It sends the whole conversation as `state` (tool results replaced by a placeholder note), fitted into a 25,000-token budget by staged truncation (tool inputs cut to 1000, then 200, then 60 characters; old text abridged head and tail; old messages collapsed to a count). Two Noul questions per tool call: "should the call stay... and should the result stay verbatim." It runs as a Claude Code plugin, but not on the classic hook family — it uses the early-access, opt-in "function hooks" surface (`session.compact`, `turn.complete`), because rewriting messages is something the classic hooks cannot do.

**jev-codex-router** deliberately avoided a hook: a `hook/` directory (a LiteLLM callback tap) is "kept for reference" only. The shipped design is a local server registered with a separate, third-party proxy tool called "Codex Router" (not an OpenAI feature) through its own "generic provider" extension point. Reported: "The decision costs ≈ $0.00003 and ≈ 0.6 s per turn," with "Measured savings: ≈ −60% vs a full-frontier baseline on a 7-day replay of 237 real turns." A 0.5 confidence gate falls back to a middle tier rather than the frontier model, because frontier fallback "eats ~80% of the savings."

**codex-context-diet** is the clearest proof of a real sub-second Jev call inside a production hook. Its `hooks.json` (read directly) registers `PostToolUse` (matcher `.*`, 10-second timeout), `SessionStart` (5 s), and `UserPromptSubmit` (5 s) — the same event names and JSON shape as Claude Code's classic hooks. Five literal Noul questions per tool result (`needs_contents`, `replaceable`, `keep_call`, `agent_directed`, `behaviour_change`) decide whether to truncate output; a prompt guard asks two more (`touches_production`, `irreversible`) and published a 10-prompt table where every safe prompt scored 0.17 or below and every risky one 0.66 or above, against its 0.7 threshold. Measured hook cost: "the whole process took 1.07 to 1.94 s" per cold invocation, and "An earlier 2 s deadline silently timed out on two of eight real invocations." It is an explicit, credited fork of fast-jev-compaction, ported from Claude Code to Codex.

**pi-heed** checks every side-effecting Pi tool call against constraints the user stated in plain language ("Review only. Don't modify any files."), keeping a structured policy (`DENY`/`ALLOW`/`REQUIRE_CONFIRMATION`) that Jev only updates, never authors. Its own 15-experiment log is unusually rigorous: "Ask about intent, not a taxonomy" lifted accuracy from 71% to 93%; "Ask exactly what you mean: 'explicitly forbidden' ≠ 'implied'" fixed 27 false positives. Measured latency: "1 / 4 / 8 questions: 274 / 273 / 276 ms" in one request — flat — but "8 parallel: ~650 ms," meaning separate parallel calls cost more than one batched call.

**pi-warden** judges every Pi `write`/`edit` against a project's `pi-warden.md` rules and quotes the broken rule back to the agent instead of showing a dialog. A hold requires a hard-coded destructive pattern or `irreversible` at 0.7 or above: "Patterns set the floor and Jev can only raise it." Across 321 sessions (17,160 guarded calls): "42 holds, and my next message approved 5, so 37 stood." A controlled test found 5 of 60 and 1 of 90 rule violations in unguarded control cells, versus zero with the guard on.

**Bicameral** names its architecture directly: "System 2 (any LLM Pi runs) writes the code," "System 1 (TypeSafe Jev...) returns typed probabilities," and "Deterministic policy code turns those scores into allow/confirm/block/warn/steer." Its `Gate` reflex prefetches on `message_update`, before the model finishes streaming its tool call, and produced this real verdict: "Blocked: this command appears to send local data, code, or credentials to a destination outside this machine (exfiltration p=0.91)." It is the only project here that redacts the outgoing state by pattern before sending: "private keys, JWTs, AWS key ids, and high-entropy assignments" become `<REDACTED:kind>` (a JWT is a JSON Web Token; AWS is Amazon Web Services). Its own README claim that "the GitHub remote is private until launch" is stale — the repository is confirmed public.

**pi-jev-compaction** clears stale tool output once a session passes 65% of context, protecting the newest 12,000 tokens, asking Jev about up to 16 large outputs per request. A cleared result becomes a marker pointing at a retrieval tool rather than being deleted, and the project states its own limit bluntly: "this is not a redaction service."

**DiffJury** is a hosted web app: paste a public pull-request URL, and it sends one Jev call with nine parallel questions — `risk` (Score), `review_depth` (Choice), `needs_design`/`needs_security`/`merge_blocker` (Noul), `missing_tests`/`docs_debt`/`blast_radius` (Score), `verdict` (Choice). The key is server-only, "never exposed to the browser."

**jev-review-action** is a GitHub Action, not an agent plugin: "Only Jev is used... There is no text-generation model, autonomous agent, or hosted bot server." It checks a pull request or a submitted catalog entry against a maintainer-authored JSON policy of yes/no criteria plus one category Choice, posting one fixed-template comment with a decision of recommended, needs-review, not-recommended, error, or skipped.

**"Clean Code Judge"** — no repository by that exact name exists; the closest real match is frostney/clean-code-review. It judges each changed file against Robert C. Martin's *Clean Code* with Jev, then a separate prose-writing model ("Luna") drafts the review from Jev's findings. The same review is exposed as an MCP server (`review_pull_request`, `review_pasted_code`); "a 24-file PR costs about $0.02 to judge and review."

**routeKit** is a plain library, not a hook or service: an agent calls `router.route(...)`, Jev answers four normalized signals (`difficulty`, `reasoningNeed`, `ambiguity`, `toolComplexity`), and a separate deterministic policy engine picks the model: "Jev does not choose the model. It produces normalized task requirements."

**jev-mcp (Node)** exposes eight tools (`jev_verify`, `jev_screen`, `jev_find`, `jev_rerank`, `jev_classify`, `jev_decide`, `jev_compare`, `jev_extract`), each documented with a live example. `jev_screen`'s recommendation is fully mechanical: "injection probability 0.99 >= block threshold 0.75." Four backing providers are auto-detected by which key is set, and it warns that "Some MCP clients filter the environment before spawning servers, which silently drops TYPESAFE_API_KEY."

**jev-mcp (Python)** is an unrelated, independently authored project that only shares a name with jkudish's — not a Node/Python pair from one codebase. It exposes seven differently named tools (`jev_ask`, `jev_classify`, `jev_score`, `jev_check`, `jev_match`, `jev_screen`, `jev_health`) and reports real field data: "Clean labels at confidence 0.8 to 1.0: 95% agreement" and "Reversing criteria order: 32 of 200 choices flipped." Its install script exposes the key briefly "in the process list."

**typesafe-mcp (Go)** is a single static binary exposing one tool, `evaluate`, taking `state` plus typed `questions` ("Give your AI agent typed decisions instead of free text"). One command, `evaluate setup mcp`, registers it with Claude Code, Claude Desktop, and Codex at once by detecting each CLI on the path; `evaluate setup pi` writes a native Pi extension, since Pi has no MCP client. It retries HTTP (Hypertext Transfer Protocol) 429/529 responses with backoff.

**typesafe-ai/skills**, the vendor's own repository, is a minimal Claude Code plugin (`plugin.json`, `marketplace.json`) holding one file, `skills/typesafe-ai/SKILL.md`. It installs into Claude Code with `claude plugin marketplace add typesafe-ai/skills` then `claude plugin install typesafe@typesafe-ai`, or into any other agent with the third-party `npx skills add typesafe-ai/skills --skill typesafe-ai`. Its instruction defers to the vendor's live documentation rather than embedding API details: "Read the live docs... This skill gives direction; the docs carry current concepts."

**codex-skills issue 66**, titled "Evaluate TypeSafe Jev as a calibrated judgment tier for #64/#65 workflow gates," is an open, zero-comment investigation issue, not a finished integration: "This is an investigation issue only... Do not implement the seam." Its proposal is the clearest single statement of the pattern this ecosystem converges on: "Jev returns probabilities; deterministic code in the hooks layer consumes them," logged with "{question payload, noul/score, threshold applied, model version}." It flags Jev's own published weaknesses — "literal reading," "weak math/counting/dates" — as things each proposed gate must be checked against before use.

**The two madewithjev.com "builds"** are the thinnest sources here, both snippet-only with no code shown. "Jev as an agent safety monitor" reports only "caught most attacks with almost no false blocks, and much faster than Gemini." "Slack agent, twice as fast" reports only a 2x speedup from "classifying the best skill, tool and params" before handing the request to the agent. Neither names a state format, exact question wording, or a repository.

## 3. Patterns worth copying, ranked

1. **Code owns the state transition; Jev only supplies a probability.** The organizing principle behind everything else, stated directly in pi-heed ("code handles control flow; Jev provides common-sense perception") and mandated in codex-skills issue 66. Never let a typed answer execute an action by itself.
2. **A three-way band, not one cutoff, where the uncertain middle always resolves to the cheaper mistake.** codex-context-diet: "Uncertainty resolves to the side that costs tokens rather than the side that loses information." pi-warden: hard-coded patterns set the floor, and Jev can only raise it, never lower it.
3. **Batch every question about one piece of state into a single request.** pi-heed measured 1, 4, and 8 parallel questions in one call at 274, 273, and 276 milliseconds — flat — while running the same questions as separate parallel requests was slower. The single biggest lever for hook speed.
4. **Ask one literal, narrow condition per question, never a compound or taxonomy question.** codex-context-diet's own fix moved a wrong answer from a 0.89 score to a correct 0.03 purely by renaming the condition being asked about; pi-heed found the identical lesson independently.
5. **Prefetch the judgment while the model is still streaming its tool call.** Bicameral scores on `message_update`, before the full `tool_call` event exists, so the Jev round trip overlaps the model's own token generation; pi-heed reports a real blocked write with effectively zero perceived wait.
6. **Redact the outgoing payload by pattern, not just by truncating its length.** Only Bicameral does this (keys, tokens, and high-entropy strings replaced before any network call). Everyone else truncates by character count, and pi-jev-compaction says outright that is not the same thing.
7. **Log every verdict locally — the question, the threshold, the pinned model version — and keep that log out of the model's own context.** Bicameral's audit entries "do NOT enter the LLM context"; codex-skills issue 66 requires pinning `jev-1.13.0` rather than the moving `jev-latest` alias so a verdict can be re-judged later.
8. **Fail open by explicit, documented policy, and say which side of each gate should fail open.** pi-heed, pi-warden, jev-router, and codex-context-diet all let the agent proceed on a Jev timeout or error; codex-context-diet's tunable deadline exists specifically because an earlier fixed one silently failed in production.
9. **A staged degradation ladder beats one truncation cut.** fast-jev-compaction only advances to a more destructive truncation stage if the previous stage did not free enough space, so short sessions never pay for the aggressive stages.

## 4. Mistakes and gaps observed

**Thresholds shipped without project-specific evaluation.** Most defaults (0.5, 0.7, 0.75, 0.8, 0.9) come from TypeSafe's own published cookbooks, not from the adopting project's own measurement — several say so themselves: jev-review-action calls its thresholds "provisional," jkudish/jev-mcp calls its own "starting points... Tune them against your own data," and blakestone-x/jev-mcp says to "validate thresholds and outputs against your own data." Only pi-heed (211 labeled decisions), pi-warden (150 paired runs, 17,160 guarded calls), and codex-context-diet (a 10-prompt calibration table) actually measured their own default before shipping it.

**Key handling ranges from careful to leaky.** codex-context-diet's key is "never written to stdout, stderr, the log, or the cache" — a good baseline. Against that: gargpratyush/jev-router writes raw prompt text and full Jev requests and responses to a plaintext temp-directory file per session; blakestone-x/jev-mcp's registration helper exposes the key "in the process list" and writes it in plain text into a config file; jkudish/jev-mcp warns that some MCP clients silently strip environment variables, producing a confusing failure instead of an obvious one.

**Truncation is routinely conflated with redaction.** Only Bicameral scrubs secrets by pattern; every character-count-based truncation scheme still sends whatever survives the cut, and pi-jev-compaction is the only project honest about that gap in its own documentation: "this is not a redaction service."

**The advertised sub-second latency is the network call, not the hook.** codex-context-diet is the only project that measured a real end-to-end hook: 1.07 to 1.94 seconds per cold invocation, against a roughly 130-500 millisecond Jev call reported elsewhere, because each invocation pays for a new process and connection. jev-codex-router and typesafe-mcp both avoid this with a persistent local server instead of spawning fresh per call — treat that as required, not optional, for a hook firing on every tool call.

**Two sourcing gaps.** codex-skills issue 66 is open with zero comments — a proposal, not a resolved discussion; its scope note says implementation "becomes a separate issue; this one closes on evidence." And no project found anywhere in this research integrates Jev with Gemini or a Qwen-based coding agent; the ecosystem's first three days concentrate entirely on Claude Code, Codex, and the Pi coding agent.

## 5. Hook events and extension points proven viable for a sub-second Jev call

**Claude Code.** The classic, stable, command-based hook family (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `SessionStart`, `Stop`, `PreCompact`) has zero confirmed use for a Jev call among these projects. jev-router bypasses hooks entirely with a proxy wrapper. fast-jev-compaction, the one project running inside the Claude Code process, needed to rewrite session messages — something the classic hooks cannot do — so it used the early-access, opt-in "function hooks" surface instead (`session.compact`, `turn.complete`, gated on `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1`, documented as unstable across releases). A Claude Code compaction plugin for this fleet should expect to need that same surface, not `PreCompact`, and should treat the instability warning as real.

**Codex.** codex-context-diet confirms Codex's plugin hooks use the identical event names and JSON shape as Claude Code's classic hooks (`PostToolUse`, `SessionStart`, `UserPromptSubmit`), and that a sub-second Jev call runs inside all three at a measured 1.0-1.9 second real-world cost against a 5-10 second budget. Separately, jev-codex-router shows per-turn routing is better served by an inline provider extension point than by a hook: it abandoned an early "LiteLLM callback tap" hook for a standalone server registered as a third-party "Codex Router" tool's generic provider — a community add-on, not an OpenAI Codex feature.

**Gemini and Qwen.** No evidence found in this research. **Pi** (not one of the fleet's four target agents, but the most heavily represented agent here after Claude Code) uses its own distinct hook vocabulary — `tool_call`, `tool_result`, `message_update`, `turn_end`, `before_agent_start`, `session_start` — conceptually similar to Claude Code's and Codex's pre/post-tool and session-start hooks, but named differently; useful mainly as a reference if the fleet ever needs to translate a hook design across agents.
