**H-01 is the finding I would hold a merge for, and it is a two-line fix.** The cycle added a
careful safety branch: on `subprocess.TimeoutExpired` the writeback returns `retryable: False` with
the message "Killing it does not kill the mission-control process it launched, so a write may still
be in flight: read the card before doing anything else". That branch can never run. The module's own
command runner is bound unconditionally at `orchestrate.py:1628` (`run = _subprocess_run`), and
`_subprocess_run` catches `TimeoutExpired` itself and, under `check=False`, returns
`CompletedProcess(returncode=124, stderr="timed out")` rather than re-raising. I drove it:

```
run(['sleep','5'], check=False, timeout=1)
  -> CompletedProcess, returncode 124, stderr 'timed out'   (no exception)
```

So control falls to `orchestrate.py:2403`, which returns `{"status": "failed", "error": "timed
out"}` — a record with **no `retryable` key**, which `_write_is_retryable` defaults to `True`. The
operator is therefore pointed at the retry door in exactly the situation the dead branch was written
to keep them away from it. And `plugins/orchestrate/CHANGELOG.md:86` ships the claim: "a genuine
timeout says explicitly that a write may still be in flight." It does not. No test drives the
timeout path — the two tests that mention it pin `reconcile_timeout`'s arithmetic only.

This is the single reason the operational-safety gate fails. Weigh it honestly: it bites only on a
real controller timeout past 390 seconds, the controller is idempotency-keyed so a raced retry
coalesces rather than double-writing, and the pre-change behaviour was the same generic failure — so
this is an unfulfilled improvement rather than a regression. But it is a new safety mechanism that
does not work, and a shipped release note that says it does.
