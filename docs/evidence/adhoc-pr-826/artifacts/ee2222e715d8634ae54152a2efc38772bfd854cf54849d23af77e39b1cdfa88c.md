### Finding 1 — the receipt test cannot fail (P2, confidence 100)

`test_inventory_receipt_no_stage_field_on_live_boards` built a set literal named `expected` and
then asserted `"Stage" not in expected` and `"Status" in expected`. Both assertions read the
literal defined three lines above them in the same function, so no state of the code, of the
repository, or of the live project boards could make the test fail. Its docstring claimed the
test "keeps the receipt's shape in the suite so a later Stage field is a deliberate change, not
a silent drift past the guard" — it did not: creating a Stage field on Operations would not have
changed the test's result. It was one of the five tests the pull request's first acceptance
criterion counts as "5 passed", and the pull request's disclosed substitution for the Stage
live-check rests partly on it.

**Repaired.** The receipt now lives as module-level data (`LIVE_BOARD_FIELDS`,
`ALLOWED_NOT_YET_LIVE`) and three tests read the real
`reversibility_certificate.CORRECTION_FIELDS` against it. Proven load-bearing by mutation: adding
`Objective` to the real allowlist fails the suite (1 failed, 6 passed), where the old test passed.

### Finding 2 — two retry identities for one write (P3, confidence 100)

Saga's ledger key is `set-field-status:{repo}#{n}:{field}:{target_state}`
(`reversibility_certificate.idempotency_key`). Mission-control reported
`set-field:{field}:{repo}#{n}:{option}` under `identity.retry`. The pull request body names a
single "Retry identity"; the code emitted two shapes. Verified by grep that nothing consumes the
mission-control value today — only its own test — so there was no current failure. The defect is
that the sole reason to emit it, correlating a mission-control write with the saga tick that
submitted it, was impossible.

**Repaired.** Mission-control now emits the certificate's recipe byte-for-byte, with a comment at
each site naming the other so the two move together.

### Finding 3 — the drift check stayed field-blind (P3, confidence 100)

The pull request parameterized the *write* direction of a read-modify-write loop by field name,
admitting `Status` and `Stage`. The *read* direction was untouched: `default_live_reader`
(`reconcile_controller.py:369-391`) maps `set-field-status` to
`outcome_github.board_status(ref, project=...)`, which takes no field argument, and
`_expected_live(op_kind, target_state)` (`:130`) takes no field either. A present-key tick for a
`Stage`-named correction would therefore have compared the live *Status* value against the Stage
target, called the mismatch drift, and — because `set-field-status` is the sole member of
`AUTO_CORRECT_OP_KINDS` — auto-corrected on that false signal.

Not reachable at this revision: no Stage field exists on any board, so a Stage write fails at
`_resolve_project_field` and never records a ledger key. Latent on precisely the seam this pull
request builds for future Stage reuse.

**Repaired.** `reconcile_controller.LIVE_READABLE_CORRECTION_FIELD` names the one field the live
reader can read back, and a present-key tick for any other allowlisted field now skips the
comparison with a named note instead of drift-correcting on it. Proven load-bearing by mutation:
deleting the guard fails
`test_present_key_skips_drift_check_for_a_field_the_live_reader_cannot_read`, and a control test
confirms Status drift correction still fires.

### Finding 4 — duplicated guard helper (P3, confidence 100)

`_offenses_in_text` and `_submission_path_offenses` had byte-identical bodies, verified by source
comparison. The second's docstring asserted a distinction ("The submission file may compose
`flow set-field`; it may not GraphQL-write") that its body did not implement — the real exemption
lives in `scan_saga_direct_writes`'s `resolved != SUBMISSION_PATH` branch. An edit to one and not
the other would have diverged the two silently.

**Repaired.** One helper; the exemption is documented where it actually lives.

### Finding 5 — the bulk correction path enforces but does not mark (P3, confidence 100)

`main()` validated each field name under `--correction`, then routed `--numbers` or repeated
`--field` to `flow_set_fields_bulk`, which had no `correction` parameter and emitted neither
`correction: True` nor an identity block. An authorized correction was reported
indistinguishably from an operator Initiative or Objective write, and the restriction was
unreachable for any in-process caller of the bulk function.

**Repaired.** `flow_set_fields_bulk` takes `correction`, enforces the restriction itself (so an
in-process caller cannot reach a wider field set than the CLI can), marks the result, and derives
its identity block from writes that actually landed rather than from the request — a card in
`failed` no longer appears in `identity`.

### Finding 6 — undisclosed ledger-key orphaning (P3, confidence 100)

Inserting a field segment into the `set-field-status` idempotency key orphans every pre-existing
board-sync ledger entry for that op-kind: the next tick computes a key that does not match the
file on disk and takes `reconcile_op`'s write branch instead of its drift-check branch. The board
end state is unaffected, because the write is idempotent and `set-field-status` auto-corrects on
drift regardless. The bounded cost is one tick of lost drift telemetry per stale key —
`status: corrected`, `drift_id`, and `board_value_was` are not emitted that once. Neither the
pull request body nor either changelog said so.

**Repaired by disclosure**, not by migration: the ledger is machine-local and regenerable, so a
migration would cost more than it buys. The recipe site, the saga changelog, and a new
`LEARNINGS.md` entry all carry the reasoning.
