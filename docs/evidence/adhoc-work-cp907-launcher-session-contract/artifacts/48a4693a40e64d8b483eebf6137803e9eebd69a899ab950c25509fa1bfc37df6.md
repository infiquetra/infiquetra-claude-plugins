## The substantive defects, in the reviewers' own evidence

### security

**`SEC-01` (P1) — **flagged critical**: A staged draft whose last visual row starts with the vendor glyph is reported as affirmative EMPTY, with no note, and the launch types into it**

inspect_composer takes blocks[-1] unconditionally. A composer block ends at the first row that is not a continuation, and a new block starts at every glyph-led row, so an operator draft that SPANS a glyph-led row is split: the earlier rows holding the text stop being the box, and a trailing glyph-led row that is empty becomes the box. guard_pane_before_write then takes the EMPTY branch at launcher.py:802-805, which sets the receipt's input_box to 'empty' and returns WITHOUT appending any note, and launch() proceeds to send() at launcher.py:1401. The operator's unsent text is then concatenated with the dispatched task and submitted -- the exact harm the feature exists to prevent. Two things make this worse than the documented fail-open trade. First, the receipt records an affirmative false claim, 'empty', rather than one of the five inconclusive causes the design already carries; unlike every inconclusive state it also writes no note at all, so nothing on the run record hints that the read was ambiguous. Second, SKILL.md:43 enumerates the fail-open states as unclassifiable, not_found, unsupported_vendor, read_failed and read_timeout, so an operator reading the contract believes an 'empty' receipt means the box was empty. The plain-marker vendors are the easy case: agy and qwen use a bare greater-than sign, so a draft ending in a blank markdown quote row collapses to EMPTY. For claude the shape needs a glyph-led final row, which is what an operator gets by pasting a Claude prompt echo -- the checked-in fixture shows Claude renders its echoes with the same glyph. The suite pins the opposite behaviour as intended at test_launcher_contract.py:627, so this is a deliberate trade rather than an oversight; it is nonetheless an undisclosed one that produces a false receipt field, and the design already owns an 'unclassifiable' bucket that this case belongs in.

Evidence: `plugins/agent-launcher/skills/agent-launcher/scripts/launcher.py:802`

```
    if inspection.state is ComposerState.EMPTY:
        if receipt is not None:
            receipt["input_box"] = "empty"
        return
```

Output: 'PROMPTS ANYWAY | F pasted transcript, last row is the glyph', receipt input_box='empty', note=''. ### architecture-maintainability

**`ARCH-01` (P1): The composer loader existence guard is dead code; a missing composer.py escapes as a raw FileNotFoundError, not the named SystemExit it was written to raise**

_load_composer_module() guards with: if spec is None or spec.loader is None: raise SystemExit(...). But importlib.util.spec_from_file_location returns a fully populated spec for a path that does not exist -- it never stats the file -- so that branch is unreachable for the only failure it was written for. The real failure surfaces two lines later inside spec.loader.exec_module(module) as an unhandled FileNotFoundError. Because orchestrate.py:1640 calls _ingest_agent_launcher() at module level and does not catch it, an agent-launcher install whose manifest is present but whose composer.py is missing kills every Orchestrate subcommand -- including --help -- with a bare traceback.
