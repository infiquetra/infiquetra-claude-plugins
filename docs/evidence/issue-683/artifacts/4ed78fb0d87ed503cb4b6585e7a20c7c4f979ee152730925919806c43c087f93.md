### P2 — advisory (does not block)

| P2-1 | `plugins/team-execution/skills/team-execution/scripts/liveness_protocol.py:280-295,457-490` | `bind_identity` hardcodes `boot_id="boot-1"` and `poll` reads `/proc/sys/kernel/random/boot_id` — on Linux the two sources diverge, so the first `poll` after `open` always reports `boot-identity-changed`. On macOS both return `boot-1` so the existing tests pass, but the mismatch is real on Linux fleet hosts. The engine still fails closed (suspect), but the invariant "open id matches poll's current" is lost. Low blast radius for U6 (liveness remains usable, no data loss), and the docstring acknowledges best-effort, but the asymmetry should be closed: either `bind_identity` should also call `_current_boot_id()` for its `boot_id`, or `poll` should fall back to `identity.boot_id` when `/proc` is present and the identity was `boot-1`. | correctness | 75 | advisory |

*Why P2 not P1:* the mismatch surfaces as `boot-identity-changed` (a defined suspect class), not as a crash, data corruptor, or silent health lie. The cold-start path (`ttl-cold-start`) and phi path remain correct; the boot signal is one of three engines and its false-positive is bounded. Citing `liveness_engine.py:170-190` boot-identity branch and `liveness_events.py:641-644` projection.
