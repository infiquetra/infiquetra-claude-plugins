### F01 — a documented accessor that raises AttributeError

The "Call Order" paragraph told the reader to reach scores "from `ReviewResult.lens_scores` /
`LensReviewResult.score`". `ReviewResult` has no `lens_scores` field — it carries
`lens_results: tuple[LensReviewResult, ...]` (:901). The module's own worked example, six lines
away in the same file, correctly writes `[item.score for item in result.lens_results]`. Probe:
`'lens_scores' not in ReviewResult.__dataclass_fields__` and `not hasattr(ReviewResult, 'lens_scores')`.
This is the exact failure the leaf opens with — an `AttributeError` from following the documentation.

### F02 — "Optional" on an argument with no default

`dimension_id: str | None` is declared with no default (:300), so it must always be passed.
Probe: `ReviewFinding(...)` without it raises
`TypeError: ReviewFinding.__init__() missing 1 required positional argument: 'dimension_id'`.
The same docstring marks its real defaults explicitly ("default: False", "default: 'active'"), so
"Optional" reads unambiguously as omittable. Leaf #784 cites four wrong-keyword `ReviewFinding`
constructions among the six failed attempts it was filed over.

### F03 — a documented input vocabulary containing a return-only value

The docstring listed `'ready'` first among `session_outcome` inputs. The code accepts `pending`,
`ran`, `ran-empty`, `died`, and `not-started` (:1478-1492); everything else, `'ready'` included,
raises `ReviewConsensusError("unknown runner session_outcome")` (:1493). `'ready'` is a
`RunnerDeliveryResolution.status` value, produced when the input was `'ran'`. Probe:
`handle_runner_delivery({"session_outcome": "ready"})` raises.

### F04 — the exception hierarchy nests opposite to its names

`ReviewScoringError(ValueError)` (:140) is the root; `ContradictoryReviewEvidenceError` (:144) and
`ReviewConsensusError` (:148) each subclass it; `UnsupportedReviewResultSchemaError` (:152)
subclasses `ReviewConsensusError`. So `except ReviewConsensusError` does **not** catch a
`ReviewScoringError`. Both the constructor and `record_cycle` documented `ReviewConsensusError` for
paths that raise the other branch. Probes: `ReviewCycleState(["not-a-real-lens"])` raises
`ReviewScoringError("unknown scoring lens")`; `record_cycle` with a finding naming a dimension its
lens does not define raises `ReviewScoringError("finding 'F01' names unknown dimension ...")`. A
caller writing the documented handler silently misses both.

### F05 — a lifecycle rule that over-promises `accepted`

Step 3 read "If all lenses meet policy acceptance criteria ... the outcome is 'accepted'". A failing
`DeltaCheckResult` returns its retained lens to the failing set (:1396-1398), so a cycle whose
supplied `lens_scores` all pass can still return `repairs_requested`. Probe: passing scores plus one
failing delta-check yields `outcome == "repairs_requested"` with the retained lens back in
`failing_lenses`.

### F06 — a guard test that could not catch what it guarded

The cycle-1 test asserted substring presence (`"lens_scores" in readiness_doc`), which passes on a
reworded but still-false docstring, and executed no documented claim outside the worked example.
Evidence: findings F01-F05 were all present with that suite green.

## Repairs (cycle 2, commit `d3bc0da0`)

`except` clause)" section; `ReviewCycleState.__init__` and `record_cycle` now name the class each
path actually raises; `dimension_id` is documented as required with no default; the runner-delivery
input and return vocabularies are separated with their mapping stated; lifecycle step 3 carries the

`dataclasses.fields(...).default is MISSING` for `dimension_id`, `hasattr` for the accessor, and

every error this module raises" was narrowed to "every error class this module defines" (a bare

`ContradictoryReviewEvidenceError` description was re-pointed from the reported-overall mismatch at
:1906 — unreachable from `record_cycle`, which passes the derived overall as the reported one — to
the unresolved-critical-finding contradiction at :2087/:2092, which is the reachable trigger.
