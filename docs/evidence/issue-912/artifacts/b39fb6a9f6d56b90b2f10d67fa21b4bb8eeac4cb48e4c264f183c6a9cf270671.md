### Why each finding matters

**1. `API-18` — UTF-16 sniff branch skips the unreadable guard; parity routes a corrupt file live** (P1, api-contract, `plugins/saga/scripts/handoff_envelope.py:73`)

The decode ladder applies the no-maturity-declaration-means-unreadable guard only inside the replacement-decode branch. When the NUL-or-BOM gate at line 73 admits a non-UTF-8 file and a UTF-16 sniff succeeds on mojibake, text is set, the guard is skipped, the carrier scan finds nothing, and the reader returns None, so infer_maturity falls through to the path rule and publishes a runnable /issue --prepare command for a file it could not read. The outcome turns on byte-length parity, and the direction flipped from fail-closed to fail-open. This is a regression against b20186e9, which returned the unreadable sentinel for every one of these inputs.

*Suggested fix:* Apply the maturity-not-in-text guard to the UTF-16 sniff branch as well as the replacement-decode branch, or restrict the sniff to a genuine UTF-16 byte-order mark as cycle 4's API-16 fix request specified, dropping the NUL-in-raw-bytes clause that re-admits unmarked binary.

*Evidence:* plugins/saga/scripts/handoff_envelope.py:71-88; lens probe at bf0da80a on the exact fixture from tests/test_handoff_envelope_maturity.py:481: 5 bytes -> unknown:unreadable, no route; the same bytes plus one -> requirements-ready with a live /issue --prepare; lens probe: a docs/plans artifact declaring pending-confirmation with an embedded NUL returns pending-confirmation at odd length and plan-ready at even length; controller re-verification, executed independently against both revisions side by side: at bf0da80a the 5-byte fixture returns unknown:unreadable (no route), 6 bytes returns plan-ready (LIVE /issue --prepare), 7 bytes returns unknown:unreadable (no route), 8 bytes returns plan-ready (LIVE route); at b20186e9 all four return unknown:unreadable with no route. The regression is confirmed and the covering test passes only because its fixture happens to be odd-length; plugins/saga/CHANGELOG.md:7 states the unreadable sentinel fires when a file cannot be decoded into text carrying a maturity declaration at all, which the even-length case contradicts; uv run pytest tests/test_handoff_envelope_maturity.py -q -> 29 passed

**2. `DOC-24` — Release note claims out-of-root absolute source never falls through** (P2, documentation-clarity, `plugins/saga/CHANGELOG.md:8`)

The 0.151.0 source-path bullet states that when the re-anchored candidate is not an existing file, the original absolute file is read directly and never falls through to the path rule, which would route live. Shipped code falls through in two sub-cases of exactly that branch: when neither the re-anchored candidate nor the original absolute path exists, and when the original exists but declares no maturity. The code's own comment at handoff_envelope.py:190-193 says the opposite of the release note.

*Suggested fix:* Reword to say the declared maturity of an existing named file is never bypassed, and state plainly that a source with no readable declaration still resolves by the path rule.

*Evidence:* plugins/saga/CHANGELOG.md:8; plugins/saga/scripts/handoff_envelope.py:190-193 comment: fall through using the re-anchored subpath for the path-rule check; ran infer_maturity on an out-of-root absolute path with neither the re-anchored candidate nor the original existing -> printed requirements-ready, a live route, not a sentinel; ran infer_maturity on an existing out-of-root absolute file whose frontmatter declares no maturity -> printed requirements-ready; control: the same helper on an out-of-root absolute file declaring pending-confirmation -> printed pending-confirmation

**3. `SEC-09` — 8 KiB read truncates mid-codepoint, marking valid files unreadable** (P2, security, `plugins/saga/scripts/handoff_envelope.py:65`)

The SEC-07 repair reads exactly 8192 bytes and decodes that slice. When the boundary lands inside a multi-byte UTF-8 character the decode raises, the file has no byte-order mark or NUL so the UTF-16 arm is skipped, the replacement-decode arm succeeds but contains no maturity declaration, and the function returns unknown:unreadable. A fully valid, fully readable checked-in document then gets no durable route and the operator is told the file could not be read or decoded. This is not hypothetical: docs/plans/2026-07-05-outcome-from-objective-375-plan.md in this repository classifies as unknown:unreadable today, and 220 of 461 checked-in artifacts under SOURCE_DIRS exceed 8192 bytes and are exposed to the same byte-alignment coin flip.

*Suggested fix:* Decode the bounded buffer with an incremental decoder or trim trailing partial UTF-8 continuation bytes before decoding, so a mid-codepoint slice cannot be mistaken for a corrupt file; and only return unknown:unreadable when the original decode failure was not a truncation artifact.

*Evidence:* plugins/saga/scripts/handoff_envelope.py:65 and :82-86; Lens sweep of all checked-in .md files under SOURCE_DIRS at bf0da80a found one fail-closed: docs/plans/2026-07-05-outcome-from-objective-375-plan.md -> unknown:unreadable; controller re-verification, executed independently: scanned 461 checked-in artifacts, 220 larger than 8192 bytes, exactly one fail-closed -- the same file, 12008 bytes -> unknown:unreadable; controller mechanism check: the whole file decodes as valid UTF-8; raw[:8192].decode('utf-8') raises "'utf-8' codec can't decode bytes in position 8190-8191: unexpected end of data" with offending bytes b' U2 \xe2\x80\x94 Ne', an em-dash cut in half by the read bound; has NUL: False; the replacement decode contains no maturity declaration; Minimal reproduction, identical valid-UTF-8 content shifted by 3 bytes: size 8199 valid utf-8 True -> unknown:unreadable, then shifted 3 bytes -> plan-ready; uv run pytest tests/test_handoff_envelope_maturity.py tests/test_handoff_envelope.py -q -> 86 passed; no test covers a mid-codepoint slice

**4. `CORR-22` — UTF-16 without BOM hides declared maturity and routes live** (P2, correctness, `plugins/saga/scripts/handoff_envelope.py:73`)

NUL bytes are valid UTF-8, so raw_bytes.decode('utf-8-sig') SUCCEEDS on a BOM-less UTF-16 file. The entire decode-recovery block, including the NUL-in-raw-bytes guard written for exactly this case, sits inside except UnicodeDecodeError and therefore never runs. The result is NUL-interleaved text in which 'maturity:' is unfindable, the frontmatter reader returns None, and infer_maturity falls through to the path rule. Executed: a docs/brainstorms file declaring maturity: pending-confirmation in UTF-16-LE with no BOM returns requirements-ready -- a runnable /issue --prepare route for an artifact whose boundary the operator has not confirmed. This is the fail-open the sentinel design exists to prevent.

*Suggested fix:* Detect UTF-16 before the primary decode (BOM check plus a NUL-density heuristic on the raw bytes), or after a successful utf-8-sig decode reject text containing NUL and route it into the same recovery ladder that ends at unknown:unreadable.

*Evidence:* plugins/saga/scripts/handoff_envelope.py:70-88; probe run: utf-16 WITH BOM -> 'pending-confirmation'; utf-16-le NO BOM -> 'requirements-ready'; utf-16-be NO BOM -> 'requirements-ready'; utf-8 control -> 'pending-confirmation'; probe run isolating the mechanism: utf-16-le NO BOM utf-8-sig decode SUCCEEDED -> except-branch never runs; startswith('---')=False; 'maturity:' in text=False; git show 3b2b7083:plugins/saga/scripts/handoff_envelope.py shows no frontmatter reader at all, so the reader and this hole are both new in this change; grep for utf-16 in tests/test_handoff_envelope_maturity.py returns nothing; the only BOM test at :346 uses a UTF-8 BOM; tests/test_handoff_envelope_maturity.py:530 skips files on UnicodeDecodeError, so the repository-wide vocabulary invariant also exempts such a file

**6. `AM-22` — Unterminated frontmatter falls through to path rule on a bulleted maturity** (P2, architecture-maintainability, `plugins/saga/scripts/handoff_envelope.py:123`)

Two owners define 'a visible maturity declaration' and they disagree. The non-delimited carrier arm accepts a bullet- or indent-prefixed maturity line; the shared helper the unterminated arm calls requires column 0. So a docs/plans file containing '---' then '- maturity: pending-confirmation' with no closing delimiter yields handoff_maturity 'plan-ready' and a runnable '/issue --prepare ... --maturity plan-ready'.
