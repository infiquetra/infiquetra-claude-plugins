## 2. Planned behavior vs. improvised recovery vs. environmental noise

**Planned and executed as written (the contract worked):** the S0 preflight with recorded command
templates and fresh re-validation; one plan → one broad doc review → validate-then-repair (no
second broad review); per-unit briefs carrying the S3 dispositions inline; lane serialization and
the shared-file collision rules; one Saga Code Review process per frozen revision with typed
outcomes; globally serialized merges with re-resolved versions; the #692 draft-and-park gate; the
repository-freshness first-action (`git fetch && git merge origin/main`) in every unit; board
writeback at every transition; evidence-gated cleanup.

**Improvised during the run (worked, but was not in the contract):**

1. **Out-of-band pushes via plain Herdr shell panes.** The session pre-push gate's width-brittle
   assert blocked every in-session push; pushes moved to hook-free shell panes with CI as the
   arbiter, disclosed per push, and the `PUSH-NEEDED <leaf> sha=<sha>` handoff became the standing
   reviewer protocol (session-only convention; see §3.1's evidence note). One reviewer
   independently landed a repair via the GitHub API with the same disclosure (PR #789). The run's
   one blocking typed outcome (PR #788's initial `repairs_requested`) existed solely because this
   push path was not yet established; the out-of-band push cleared it and a superseding
   `accepted` comment upgraded the record.
2. **Evidence-based settlement watchers.** Herdr `idle` flickers between an agent's own polling
   turns produced two false settlements early (both units were mid-work with uncommitted output).
   All later watchers keyed on durable evidence only — a commit on the branch, an open PR, a typed
   reply — and never misfired. The same evidence model shipped *inside* the run as leaf #780.
3. **Reviews as direct Herdr sessions.** The orchestrate driver enforces exactly one Code Review
   controller per run, which cannot represent twenty per-unit processes; reviews #779 onward ran
   as direct sessions launched with the contract's validated T5 template in detached worktrees,
   fetching `pull/<n>/head` into their own `review/<n>` branches. Note an attribution gap in the
   durable record: the mapping note in #787's opening comment describes reviews as "ordinary
   orchestrate units" — accurate only for review-786, the sole review with an orchestrate task
   brief (`.orchestrate/tasks/review-786.task.md`); the direct-session mechanism that actually ran
   from #779 onward is corroborated by the PR records themselves (for example, PR #805's review
   names worktree `rev-781` and branch `review/781`) but was never written back to #787.
4. **Per-merge reintegration of surviving PRs.** Because every plugin PR edits
   `.claude-plugin/marketplace.json`, each serialized merge re-dirtied the still-open PRs; the
   standing response was an immediate `merge origin/main` + out-of-band push (PR #805 needed
   three).

**Environmental noise (neither planned nor a defect in the run's own mechanism):** the ~40-column
hook terminal that makes argparse wrap (root cause of #792); GitHub's transiently stale
`DIRTY`/`UNKNOWN` merge-state after pushes (two "conflicts" resolved by clean local merges);
Antigravity's catalog endpoint timing out at S0 (recovered before wave 1, with a recorded
fallback rule that was never needed); the Antigravity CLI survey dialog absorbing one session's
attention mid-gate.

## 3. Analysis

### 3.1 Proven success factors (candidates for standard mechanism)

The matrix in §4 carries the full list. The three load-bearing ones:

- **A decision-complete contract as a single issue, executed literally.** Every mid-run question
  ("who reviews", "what merges when", "what happens at the gate") had a written answer in #787,
  so recovery actions were selections, not inventions. Evidence: no unplanned halts across 20
  leaves — the only designed halt was the #692 gate, and the one blocking typed outcome (PR #788,
  `repairs_requested`) cleared without stopping the run.
- **Validate-then-repair between every producer and consumer.** The S2 review's 17 findings were
  each independently checked against the tree before repair (17/17 genuine — including a P0 that
  would have re-broken a shipped fail-loud path); unit briefs then carried those dispositions
  inline so downstream agents could not miss them. The one leaf that skipped this shape (none did)
  does not exist to compare against — the counterfactual is the S2 record itself, which shows the
  plan as first written would have misdirected at least five units (F1, F5, F6, F7, F8).
- **Typed, durable evidence at every boundary.** The signals with durable artifacts: `UNIT-DONE`
  (in 19 unit briefs under `.orchestrate/tasks/`), `UNIT-PARKED` (in `b7-692.task.md`),
  `REVIEW-DONE` and the typed-outcome PR comments naming every reviewed SHA. These made
  transitions machine-checkable and made the two false settlements detectable within one poll.
  Honesty note: the `PUSH-NEEDED #n sha=…` handoff left **no durable artifact** — it lived only
  in session pane text — and the pre-dispatch frozen-SHA equality checks (worktree HEAD == PR
  head) are likewise session-observed; what survives durably is each review comment naming its
  reviewed SHAs. The pattern's durable half is the standard; the session-only half is why backlog
  item 5 proposes documenting the handoff.

### 3.2 Operator-runbook guidance (should stay explicit per run)

Vendor pools, models, effort tiers, concurrency caps, and account selection are **per-run
operator inputs** — this run's Antigravity/Grok/Muse/Opus assignments are one instantiation, not
a default. What should be standard is the *declaration shape*: a pools table with priority order,
per-pool caps, launch templates validated at S0, and an explicit statement of which pools went
unexercised at run end. Also operator-owned per run: the decision gates (which leaves park), the
merge authority, and any mid-run rulings (recorded as comments so they become durable evidence).

### 3.3 Plugin/tooling changes the evidence supports (proposed, not implemented)

See the backlog in §6. The strongest evidence-backed items: the width-stable gate assert (#792,
already filed), first-class multi-process review support in orchestrate (the one-controller limit
forced the direct-session workaround twenty times), and an orchestrate-native evidence-settlement
watcher (the run hand-rolled many single-purpose monitor scripts around the same three evidence
signals — session-observed; the scripts were not preserved).

### 3.4 Failures, workarounds, unresolved risks (follow-up material)

- #792 remains open (width-brittle assert); until fixed, any in-session push in this repo can be
  blocked by a false positive.
- Environment-coupled tests reached CI once as a cause (PR #805, red across four runs) despite
  local review — local review runs on a machine where the launcher exists; CI is the only honest
  arbiter for environment coupling.
- Post-merge CI on `main` at the closing HEAD `2660d0c2` was red on one apparent race-test flake
  (`test_two_receivers_race_one_acceptance`, run 32759666600) while the local gate was green and
  the closing comment reported only the local gate — the run's own "CI is the arbiter" rule was
  applied everywhere except its closing quality signal. `main` went green at `675c80ff`; the
  flake itself is undiagnosed and is follow-up material.
- PR #810's first CI run was red on three jobs, including the journal newest-first guard catching
  a misplaced journal entry — the same defect the operator caught by reading the diff; the guard
  works and the entry-placement rule belongs in any run's closing-bookkeeping checklist.
- Reviewer sessions cannot push through the session gate; the PUSH-NEEDED handoff is a working
  protocol but adds an orchestrator round-trip per repair cycle.
- Pane-state settlement remains untrustworthy for vendors whose sessions idle between
  self-scheduled polls; #780's merged fix addresses orchestrate's own `settle`, but ad-hoc
  watchers outside orchestrate must still key on evidence.
- GitHub merge-state staleness (`DIRTY` on branches that merge cleanly) cost several needless
  reintegration checks; treat `mergeStateStatus` as eventually consistent.
- Five operator-typed lines in reviewer panes never submitted (Enter did not register in those
  TUIs); the orchestrator read and honored the intent out-of-band. Session-observed; mechanism
  not diagnosed. Risk: operator instructions silently not reaching sessions.

honoring the dependency graph, collision rules, and the decision gates below. Entry point:
invoke /orchestrate on this issue.

## 6. Proposed Claude Plugins improvement backlog (operator review required — nothing filed or implemented)

**Proven standardization (evidence: repeated, load-bearing in this run):**

1. Orchestrate: support multiple sequential/concurrent Code Review processes per run (the
   one-controller limit forced twenty direct-session workarounds). Evidence: only one review has
   an orchestrate task brief in the run record (`review-786.task.md`) while all twenty reviews
   demonstrably ran (typed comments on every PR, review worktrees/branches named in PR records
   such as #805's `rev-781`/`review/781`); the driver's single-controller refusal itself left no
   durable artifact and is session-observed.
2. Orchestrate: evidence-based settlement everywhere pane state is currently consulted (merged
   for `settle` via #780; the same rule for `wait` debounce and status display).
3. Saga pre-push gate: width-stable environment (already filed as #792 — the one backlog item
   that exists as an issue, filed mid-run with operator's directive).

**Optional operator guidance (works, but is judgment, not mechanism):**

4. Contract template (§5) as the parent-issue shape for objective-wide runs — **generalized from
   one run (n=1)**; re-evaluate for "proven" status after a second objective-wide run, and scale
   its ceremony down for small runs per §8.
5. The PUSH-NEEDED reviewer handoff: document it in the orchestrate skill as the pattern for
   session-gate-blocked pushes, rather than building tooling for it (session-only convention in
   this run — documenting it is also what would make it durable).
6. Reintegrate-after-every-merge as standing merge-queue practice.
7. Per-run pool declaration table (priority, cap, template, exercised-or-not at closeout).

**Follow-up investigation (evidence insufficient to prescribe):**

8. Why operator-typed Enter did not register in reviewer TUIs (five session-observed instances;
   affects operator ability to steer background sessions directly).
9. Whether unexercised pools 2/3 dispatch correctly when steady-state readiness exceeds pool-1
   capacity (this run never reached that state).
10. Environment-coupled-test lint: whether a cheap static check ("test resolves a real tool on
    PATH") could catch the #805 class before CI. Risk of over-engineering: high — evaluate
    against actual recurrence first.

contract declares its own shared files); this repo's journal/retro conventions; anything that is
a per-run operator choice (vendor names, caps, gate leaves) — the runbook standardizes the
declaration shape, never the choices.
