# Issue Templates Reference

Rendered reference for all 6 Infiquetra issue templates. Templates live in
`infiquetra-sdlc/.github/ISSUE_TEMPLATE/` and are automatically used by `gh issue create --template <name>.yml`.

---

## Capability Template

**File**: `.github/ISSUE_TEMPLATE/capability.yml`
**Title prefix**: `[CAPABILITY] `
**Labels auto-applied**: `capability`, `needs-analysis`

### Required Fields
- **Objective**: One-sentence description of what this capability delivers
- **Business Value**: Critical / High / Medium / Low
- **Context Links**: Links to Blueprint requirements, specifications, and ADRs
- **Acceptance Criteria**: Testable criteria that define "done"
- **Risk Level (QE)**: Low / Medium / High / Critical
- **Capability Size**: XS (1-2 days) / S (3-5 days) / M (1-2 weeks) / L (2-4 weeks) / Unknown
- **Technical Risk**: Low / Medium / High / Very High

### Optional Fields
- PM Validation (outcome connection, discovery insight, scope validation)
- Technical Approach (can be generated by Claude during Analysis)
- Success Metrics (performance target, availability target, business metric)
- Dependencies (other capabilities, external systems, infrastructure)
- Parent Objective (`objective:platform-launch`)
- Parent Initiative (`initiative:olympus-v1`)
- Test Strategy (QE fills in)
- Automated Tests checklist
- Manual/E2E Tests checklist
- AI Generation Instructions
- Context Completeness %
- Risk Description

### Example (filled in)

```markdown
Title: [CAPABILITY] Implement user onboarding service with REST API

Objective: Implement user onboarding service with API, database persistence, and monitoring
Business Value: Critical
Context Links:
- Requirements: https://github.com/Infiquetra/infiquetra-blueprint/blob/main/requirements/onboarding.md
- Specifications: https://github.com/Infiquetra/infiquetra-blueprint/blob/main/specifications/services/onboarding-service.md

Acceptance Criteria:
- [ ] POST /api/v1/onboard accepts user onboarding requests
- [ ] Data persists to database with correct schema
- [ ] Monitoring and logging configured
- [ ] Integration tests pass with 90%+ coverage
- [ ] Deployed to non-prod and validated

Risk Level: Medium
Capability Size: M (1-2 weeks)
Technical Risk: Medium

Parent Objective: objective:platform-launch
Parent Initiative: initiative:olympus-v1
```

## Enhancement Template

**File**: `.github/ISSUE_TEMPLATE/enhancement.yml`
**Title prefix**: `[ENHANCEMENT] `
**Labels auto-applied**: `enhancement`, `needs-analysis`

### Required Fields
- **Objective**: What are we improving and why?
- **Current State**: What exists today and what's the problem?
- **Proposed Improvement**: What will we change?
- **Acceptance Criteria**: Testable criteria for "done"
- **Risk Level**: Low / Medium / High
- **Review Level (QE)**: Spot Check / Standard Review / Deep Review

### Optional Fields
- Context Links (related capabilities, specs)
- Performance/Quality Target
- Estimated AI Generation %
- Risk Description
- Parent Objective and Initiative
- Testing Approach
- Automated Tests checklist
- Manual/E2E Tests checklist
- AI Generation Instructions

### Example (filled in)

```markdown
Title: [ENHANCEMENT] Add caching layer to reduce API latency

Objective: Add Redis caching to reduce API latency from 800ms to 200ms
Current State:
- API currently takes 800ms (p95)
- Users experiencing noticeable delays during peak hours
- Database reads on every request, no caching

Proposed Improvement:
- Add caching with 5-minute TTL for metadata
- Cache invalidation on updates
- Fallback to database on cache miss

Acceptance Criteria:
- [ ] Caching implemented with 5-minute TTL
- [ ] API latency < 200ms (p95) under normal load
- [ ] Cache hit rate > 80%
- [ ] Cache invalidation tested and working
- [ ] Monitoring dashboard shows cache metrics

Performance/Quality Target: Reduce p95 latency from 800ms to <200ms
Risk Level: Medium
Review Level: Standard Review
```

## Defect Template

**File**: `.github/ISSUE_TEMPLATE/defect.yml`
**Title prefix**: `[DEFECT] `
**Labels auto-applied**: `defect`, `needs-triage`

### Required Fields
- **Problem Description**: What's broken? Be specific.
- **Priority**: Critical (4h SLA) / High (1 day) / Medium (3 days) / Low (when capacity)
- **Impact Assessment**: Users affected, functionality impacted, workaround available
- **Steps to Reproduce**: Numbered steps with expected vs. actual
- **Environment**: Production / Pre-Prod / Development / Unknown
- **First Observed**: Date/time
- **Frequency**: Always / Frequently / Intermittent / Rare
- **Post-Incident Review Required (QE)**: Yes (Critical) / Yes (High with learning) / No

### Optional Fields
- Error Messages / Logs
- Related Recent Changes
- Parent Objective and Initiative (if blocking)
- Root Cause Analysis (QE fills in)
- Root Cause (developer fills during investigation)
- Fix Approach
- Prevention Strategy
- Automated and Manual Test checklists
- AI Generation Instructions

### Example (filled in)

```markdown
Title: [DEFECT] API returning 500 error for all requests since 14:30

Problem Description: API (POST /api/v1/onboard) returning 500 Internal
Server Error for all valid requests. Started after deploy at 14:30 UTC.

Priority: Critical (4 hour SLA - system down, data loss, security breach)

Impact Assessment:
- Users Affected: All users attempting onboarding (estimated 1,000/day)
- Functionality Impacted: Onboarding completely broken
- Business Impact: Users unable to complete signup
- Workaround Available: Manual process (slow, painful)

Steps to Reproduce:
1. POST /api/v1/onboard with valid payload: {"userId": "123", "name": "Test"}
2. Expected: 200 OK with confirmation
3. Actual: 500 Internal Server Error

Error Messages:
ValidationError - missing required key 'timestamp'

Environment: Production
First Observed: 2026-03-17 14:32 UTC
Frequency: Always (100% of attempts)
Related Recent Changes: PR #456 deployed at 14:15 - schema change

Post-Incident Review Required: Yes - Critical defect
```

## Exploration Template

**File**: `.github/ISSUE_TEMPLATE/exploration.yml`
**Title prefix**: `[EXPLORATION] `
**Labels auto-applied**: `exploration`, `research`

### Required Fields
- **Research Question**: What do we need to learn?
- **Context**: Why do we need to know this?
- **Success Criteria**: What makes this exploration successful?
- **Timebox**: 1, 2, or 3 days
- **Deliverables**: What will be produced?
- **Key Questions to Answer**: Specific questions to investigate

### Optional Fields
- Evaluation Criteria (for option comparison)
- Investigation Approach (day-by-day plan)
- Parent Objective and Initiative
- Automated Tests (for POC validation)
- Manual/E2E Tests (for option evaluation)
- AI Generation Instructions
- Related Issues

### Example (filled in)

```markdown
Title: [EXPLORATION] Evaluate auth SDK options: Auth0 vs. Clerk vs. Supabase Auth

Research Question: Which auth SDK should we integrate for user authentication:
Auth0, Clerk, or Supabase Auth?

Context:
- Related Capability: #234 (Implement authentication flow)
- Decision to Inform: Vendor selection for Q1 MVP
- Business Driver: Need to choose vendor by March 20 to hit March 31 deadline
- Requirement: OAuth2/OIDC compliance, MFA support, <3s auth flow

Success Criteria:
- [ ] All three SDKs evaluated against defined criteria
- [ ] Options documented with pros/cons matrix
- [ ] Clear recommendation with rationale
- [ ] Cost comparison completed for 10K/100K users
- [ ] Decision documented as ADR-043

Timebox: 2 days

Deliverables:
- [ ] Comparison document in infiquetra-blueprint/explorations/auth-sdk-eval.md
- [ ] Recommendation for path forward
- [ ] Prototype code for top choice (throwaway quality)
- [ ] ADR-043 documenting the decision

Key Questions to Answer:
1. Which SDK supports OAuth2/OIDC out of the box?
2. Can all three handle MFA with <3s flow?
3. Which has the best developer experience?
4. What is total cost per 10K users?
5. Which has the fastest integration path?
```

## Context Update Template

**File**: `.github/ISSUE_TEMPLATE/context-update.yml`
**Title prefix**: `[CONTEXT] `
**Labels auto-applied**: `context-update`, `documentation`

### Required Fields
- **What's Being Updated**: Checkboxes (requirements, spec, ADR, API contract, data model, pattern, AI prompt, diagram, integration guide) — at least one required
- **Why This Update**: What triggered this update?
- **Files to Update**: Specific Blueprint repository file paths
- **Changes Description**: What's being added, changed, removed
- **Acceptance Criteria**: What must be complete?
- **Critical Context Gap?**: Yes (blocking work) / No (improving docs)
- **Documentation Type**: Requirements / Specification / Decision / Pattern / Anti-pattern / AI Prompt / Integration Guide / Architecture

### Optional Fields
- AI Prompt to Save (if documenting a successful Claude interaction)
- Related Issues (capability that triggered this, capabilities that benefit)
- Parent Objective and Initiative
- Documentation Quality Checklist
- Automated Tests (link validation, markdown linting)
- Manual/E2E Tests (accuracy review, clarity review)
- AI Generation Instructions

### Example (filled in)

```markdown
Title: [CONTEXT] Update onboarding service spec with webhook callback pattern

What's Being Updated:
- [x] Technical specification
- [x] API contract (OpenAPI spec)
- [x] Architecture diagram

Why This Update:
- Related Capability: #201 (Implement onboarding service)
- Gap discovered during: Development
- Issue: Specification didn't include webhook callback pattern for async flow
- Impact: Future developers will implement sync-only and miss the async requirement

Files to Update:
- `specifications/services/onboarding.md`
- `specifications/api/onboarding-api.yaml`
- `architecture/diagrams/onboarding-flow.py` (regenerate diagram)

Changes Description:
Adding:
- Webhook callback section to specification with examples
- Retry logic requirements (3 attempts, exponential backoff)
- Security requirements for webhook authentication (HMAC-SHA256)
Updating:
- OpenAPI spec to include webhook registration endpoint
- Architecture diagram to show async flow

Acceptance Criteria:
- [ ] Webhook section added to specification with examples
- [ ] OpenAPI spec includes /webhooks/onboard endpoint
- [ ] Architecture diagram regenerated and accurate
- [ ] Linked to Capability #201
- [ ] No broken links in documentation

Critical Context Gap: Yes - this is blocking future capabilities that need async flow
Documentation Type: Specification
```

## Objective Template

**File**: `.github/ISSUE_TEMPLATE/objective.yml`
**Title prefix**: `[OBJECTIVE] `
**Labels auto-applied**: `objective`

### Required Fields
- **Objective Name**: Clear descriptive name (no date in this field)
- **Objective Type**: Pilot / MVP / Release / Program
- **Target Date**: YYYY-MM-DD
- **Success Criteria**: What must be true for this to be complete?
- **Overall Risk Level (QE)**: Low / Medium / High / Critical

### Optional Fields
- Parent Initiative (`initiative:olympus-v1`)
- Outcome Metrics (leading and lagging indicators)
- Included Capabilities list
- Business Value
- Stakeholders (Business Owner, Tech Lead, External)
- Quality Risks (QE fills in)
- Test Strategy Overview (QE fills in)
- Learning Plan
- Delivery Risks
- Dependencies

### Example (filled in)

```markdown
Title: [OBJECTIVE] Platform Launch MVP

Objective Name: Platform Launch MVP
```

## Template Usage Notes

### Creating with sdlc_manager.py

```bash
# Launch interactive template via sdlc_manager
python3 sdlc_manager.py issue create --repo infiquetra-core --type capability

# Or use gh CLI directly with the template
gh issue create --repo Infiquetra/infiquetra-core --template capability.yml
```

### After Creation Checklist

For all issue types:
1. Confirm template auto-applied type labels
2. Run `labels auto-label` to catch content-based labels
3. Add priority label for defects
4. Add `objective:*` and `initiative:*` labels if applicable
5. Run `board add` to add to project
6. Run `labels sync-fields` to sync labels to project fields
7. For objectives: also run `milestones create` and `milestones link`

### Template Files Location

Templates deployed to repos via:
```bash
python3 sdlc_manager.py rollout deploy-templates --repo <repo>
```

Source templates in: `$INFIQUETRA_SDLC_PATH/.github/ISSUE_TEMPLATE/`
